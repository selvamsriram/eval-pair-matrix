# Short gist: memory-conflict RAG and judge-pairing

## Generator track: Generator-side paper

**Title idea:**
**When Retrieval Contradicts Memory: Measuring Parametric Override in Long-Form RAG**

**Core idea:**
This paper studies whether LLMs actually follow retrieved evidence when the provided RAG context conflicts with facts they likely know from pretraining. Using GaRAGe, we perturb every answer-containing grounding passage so the retrieved evidence consistently supports a modified fact. Then we test whether models follow the perturbed evidence, override it with the original fact from memory, hedge, or misuse citations.

**Main novelty:**
The paper is not just “models ignore context.” It measures **memory-conditioned context adherence**: whether models are more likely to override retrieval when closed-book probes show they already know the original answer. The benchmark is long-form, citation-aware, and uses globally consistent perturbations across all answer-containing passages.

**Main research question:**
When RAG evidence is internally consistent but contradicts likely parametric memory, do stronger models trust retrieval or memory?

**Key metrics:**
Context adherence rate, memory override rate, conflict awareness rate, citation misuse rate, closed-book-knownness effect, perturbation-type sensitivity, and popularity/domain sensitivity.

---

## Judge-pairing track: Evaluator-side paper

**Title idea:**
**Who Judges the Judge? Pairing Effects in LLM Evaluation of RAG Factuality**

**Core idea:**
This paper studies whether LLM judges fairly evaluate RAG answers generated by the same model, same model family, or different model families. The generated answers come from the same GaRAGe perturbation pipeline. Some answers faithfully follow the perturbed context and are therefore wrong relative to the original source; others use the original fact and are correct relative to the original source. Judges receive the original grounding passages but not the gold answer or perturbation metadata.

**Main novelty:**
The paper turns RAG evaluation into a controlled factual-error detection task with hidden perturbation labels. Instead of asking whether judges “prefer” their own outputs, it tests whether they can detect known induced factual errors and localize the contradicted claim, while measuring same-model, same-family, and cross-family effects.

**Main research question:**
Do evaluator–generator pairings affect factual error detection in RAG evaluation, especially when the answer is fluent, cited, and generated by the judge’s own model family?

**Key metrics:**
Error detection precision/recall/F1, false positive rate, localization accuracy, same-model delta, same-family delta, cross-family judge advantage, and confidence calibration.

# Dataset architecture

Create one core dataset:

## **GaRAGe-PerturbCore**

This contains only:

* original question
* original answer
* original grounding passages
* all answer-containing grounding passages
* answer-causal claim extracted from the answer-supporting evidence
* all source locations where that claim or answer-bearing value appears
* perturbed version of the claim
* all perturbed grounding passages
* perturbation metadata
* validation labels

Then create two derived datasets:

## **GaRAGe-MemoryConflict**

Used for Generator track.

Adds:

* closed-book model answers
* original-context RAG answers
* fully perturbed-context RAG answers
* labels for whether the generator followed the perturbed evidence or overrode it with memory

## **GaRAGe-JudgePair**

Used for Judge-pairing track.

Adds:

* generated answers from different models
* judge model outputs
* same-model / same-family / cross-family pairing labels
* factual error detection and localization labels

This gives you one shared infrastructure, but two scientifically distinct datasets.

GaRAGe is a strong base because it contains 2,366 questions, human-curated long-form answers, and over 35K annotated grounding passages. Each entry includes fields such as `sample_id`, `question`, `grounding`, `question_valid`, `question_false_premise`, `question_seeking`, `question_type`, `question_complexity`, `question_category`, `question_popularity`, `evidence_relevant`, `evidence_correct`, `answer_generate`, `answer_validate`, and `evidence_cited`. ([GitHub][1])

# Step 1: Filter GaRAGe examples

Use examples that satisfy:

```text
question_valid = true
question_seeking = true
question_false_premise = false
answer_validate = true
at least two grounding passages where evidence_correct = ANSWER-THE-QUESTION
```

Prefer examples where at least one answer-containing passage is cited in the human-written answer:

```text
at least one passage where:
  evidence_correct = ANSWER-THE-QUESTION
  AND evidence_cited = YES
```

But the perturbation should not be limited to cited passages. The key set is:

```text
answer_containing_passages = all passages where:
  evidence_correct = ANSWER-THE-QUESTION
```

Why this matters: if only one answer-bearing passage is perturbed while another answer-bearing passage still contains the original fact, the model may reasonably follow the unmodified passage. That turns the experiment into an inter-context conflict task rather than a clean memory-vs-grounding task.

For the first version, target:

|    Dataset size | Use case                   |
| --------------: | -------------------------- |
|    100 examples | debugging pipeline         |
|    250 examples | one-week MVP               |
|    500 examples | credible first paper       |
| 1,000+ examples | stronger benchmark release |

Stratify the sample by:

* `question_popularity`: Head / Torso / Tail
* `question_complexity`: Simple, Comparison, Aggregation, Multi-Hop, etc.
* `question_category`: science, finance, health, travel, sports, etc.
* `question_type`: slow-changing / fast-changing where applicable

GaRAGe directly provides these metadata fields, which helps you later analyze whether memory override differs by popularity, complexity, domain, and temporal sensitivity. ([GitHub][1])

# Step 2: Identify the full answer-containing passage set

For each example, construct:

```text
answer_containing_passages = passages where:
  evidence_correct == ANSWER-THE-QUESTION
```

Then identify the subset that explicitly supports the mutable answer claim:

```text
claim_bearing_passages = answer_containing_passages where:
  passage states, entails, or directly supports the selected atomic claim
```

In many examples, these will be the same set. In some examples, one answer-containing passage may support a different part of the answer. Keep both distinctions.

You want to select examples where the answer-bearing passages can be made **globally consistent** after perturbation.

Accept examples where:

```text
the selected answer-causal claim appears in all or most answer-containing passages
OR
all answer-containing passages can be rewritten consistently to support the perturbed answer
```

Reject examples where:

```text
different answer-containing passages support unrelated parts of the answer
the answer depends on too many separate claims
the perturbation would require rewriting large sections of multiple passages
the original grounding set contains unresolved disagreements
the modified answer would still be contradicted by another answer-containing passage
```

The goal is that, after perturbation, the retrieved evidence consistently points to the perturbed answer.

# Step 3: Extract one answer-causal atomic claim

From the human answer and answer-containing passages, extract one atomic claim.

Example:

```json
{
  "atomic_claim_original": "Marie Curie won the Nobel Prize in Chemistry in 1911.",
  "subject": "Marie Curie",
  "relation": "won Nobel Prize in Chemistry",
  "object": "Nobel Prize in Chemistry",
  "time": "1911",
  "claim_type": "temporal_award_fact"
}
```

A good atomic claim must be:

```text
specific
verifiable from the answer-containing passages
important to the answer
minimally perturbable
likely to be known by at least some LLMs
repeatable or harmonizable across all answer-containing passages
```

Do not perturb the whole answer. Perturb one answer-causal claim per example in the first dataset. This keeps labels clean.

---

# Step 4: Locate all answer-bearing mentions

For the chosen atomic claim, find every mention across the answer-containing passages.

Store each mention as a source location:

```json
{
  "passage_id": 3,
  "original_span": "won the Nobel Prize in Chemistry in 1911",
  "char_start": 482,
  "char_end": 530,
  "mention_type": "explicit"
}
```

Mention types:

| Mention type  | Meaning                                                 |
| ------------- | ------------------------------------------------------- |
| `explicit`    | The exact value or fact appears directly                |
| `paraphrased` | The same fact appears in different wording              |
| `entailed`    | The passage entails the fact without saying it directly |
| `table_like`  | The fact appears in a structured or list-like passage   |
| `contextual`  | The fact is distributed across nearby sentences         |

For the first version, prefer `explicit` and `paraphrased` mentions. They are much easier to perturb reliably.

Important: the perturbation target is not “one passage.” The target is the **claim across the full answer-containing evidence set**.

---

# Step 5: Create one globally consistent perturbation

For each atomic claim, create one perturbed claim and apply it consistently across all answer-containing passages that state or support that claim.

Use these perturbation types:

| Type                          | Example original  | Example perturbation     |
| ----------------------------- | ----------------- | ------------------------ |
| Entity substitution           | founded by X      | founded by Y             |
| Temporal shift                | happened in 1911  | happened in 1912         |
| Numerical shift               | 47 members        | 57 members               |
| Relation inversion            | acquired by X     | acquired X               |
| Location change               | based in Paris    | based in Lyon            |
| Affiliation change            | member of X       | member of Y              |
| Ranking/comparison flip       | largest in Europe | second-largest in Europe |
| Causal change                 | caused by X       | caused by Y              |
| Negation/modality             | is required       | is not required          |
| Multi-hop bridge perturbation | X connects A to B | Y connects A to B        |

Do not make absurd perturbations.

Bad:

```text
Marie Curie won the Nobel Prize in Chemistry in 3000.
```

Good:

```text
Marie Curie won the Nobel Prize in Chemistry in 1912.
```

For each perturbation, save:

```json
{
  "perturbation_type": "temporal",
  "perturbation_subtype": "year_shift",
  "original_value": "1911",
  "perturbed_value": "1912",
  "edit_distance_semantic": "small",
  "plausibility": "high",
  "answer_causal": true,
  "requires_multi_hop": false,
  "global_consistency_required": true
}
```

# Step 6: Create fully perturbed grounding

For each example, produce two grounding sets:

## Original grounding

```text
all original GaRAGe grounding passages
```

## Fully perturbed grounding

```text
all original GaRAGe grounding passages,
except every answer-containing passage that states/supports the selected claim is rewritten to support the perturbed claim
```

Non-answer passages remain unchanged unless they also contain the same answer-bearing claim. If a passage is marked `RELATED-INFORMATION` or `UNKNOWN` but explicitly contains the original answer value, flag it. You can either:

1. also perturb it, or
2. exclude the example if leaving it unchanged would reveal the original answer.

For a clean memory-conflict benchmark, I recommend this rule:

```text
Perturb every passage in the grounding set that contains the original answer-bearing value, regardless of evidence_correct label.
```

This prevents accidental leakage of the original fact inside the provided context.

Store all passage edits:

```json
{
  "modified_passages": [
    {
      "passage_id": 0,
      "original_passage": "... Marie Curie won the Nobel Prize in Chemistry in 1911 ...",
      "perturbed_passage": "... Marie Curie won the Nobel Prize in Chemistry in 1912 ...",
      "edits": [
        {
          "original_span": "1911",
          "perturbed_span": "1912",
          "char_start": 214,
          "char_end": 218,
          "mention_type": "explicit"
        }
      ]
    },
    {
      "passage_id": 4,
      "original_passage": "... the 1911 chemistry Nobel laureate Marie Curie ...",
      "perturbed_passage": "... the 1912 chemistry Nobel laureate Marie Curie ...",
      "edits": [
        {
          "original_span": "1911",
          "perturbed_span": "1912",
          "char_start": 72,
          "char_end": 76,
          "mention_type": "paraphrased"
        }
      ]
    }
  ]
}
```

The final perturbed context should be internally consistent:

```text
No answer-containing passage should still support the original claim.
No grounding passage should accidentally leak the original answer-bearing value.
The perturbed grounding should support exactly one modified answer.
```

# Step 7: Validate the perturbation

Every perturbation needs five validation labels.

## 1. Type validity

Does the perturbation preserve grammaticality and entity type?

```json
"type_valid": true
```

## 2. Answer-causality

Would a faithful answer to the question change if the perturbed claim were true?

```json
"answer_causal": true
```

## 3. Global consistency

Do all answer-containing passages now support the perturbed answer rather than the original answer?

```json
"global_context_consistent": true
```

## 4. No original leakage

Does the perturbed grounding avoid revealing the original answer-bearing value?

```json
"no_original_answer_leakage": true
```

## 5. Original-vs-perturbed contradiction

Does the original source clearly support the original fact and contradict the perturbed fact?

```json
"original_contradicts_perturbed": true
```

Use an LLM validator plus a human audit of 10–20%. For a one-week project, manually audit at least 50 examples and all perturbation templates.

Reject examples where the validator says:

```text
not answer-causal
too ambiguous
not globally consistent
original answer still appears in grounding
perturbation changes too much context
both original and perturbed could be true
```

# Step 9: Create Generator track view — memory conflict generation

For each `core_id`, run each generator model in three modes.

## Mode A: closed-book probe

Prompt:

```text
Answer the question using only your own knowledge. Do not use external sources.
Give a concise answer and include your confidence from 0 to 1.

Question:
{question}
```

Run 3 samples per model.

Save:

```json
{
  "core_id": "garage_core_000123",
  "model": "gpt",
  "mode": "closed_book",
  "sample_id": 1,
  "answer": "...",
  "confidence": 0.82,
  "entails_original_claim": true,
  "entails_perturbed_claim": false,
  "closed_book_knows_original": true
}
```

Define:

```text
closed_book_knows_original = true
if at least 2/3 samples entail the original claim
```

This is essential for Generator track. Without this, you cannot strongly argue parametric memory; you can only argue context noncompliance.

---

## Mode B: original-context RAG control

Prompt with original GaRAGe grounding:

```text
Answer the question using only the provided grounding passages.
Cite the passage numbers that support each factual claim.
If the passages are insufficient, say so.

Question:
{question}

Grounding passages:
{all_grounding_original}
```

Save the answer.

This tells you whether the model can answer normally with clean evidence.

---

## Mode C: fully perturbed-context RAG

Same prompt, but use the globally perturbed grounding set.

```text
Answer the question using only the provided grounding passages.
Cite the passage numbers that support each factual claim.
If the passages are insufficient, say so.

Question:
{question}

Grounding passages:
{all_grounding_perturbed}
```

Save the answer.

Here, every answer-containing passage that supports the selected claim has been modified consistently. This makes the experiment cleaner: if the model gives the original fact, it is not because another answer-containing passage in the supplied context still said the original fact.

# Step 10: Label generator behavior for Generator track

For each fully perturbed-context answer, classify it into one of these labels:

| Label                     | Meaning                                                              |
| ------------------------- | -------------------------------------------------------------------- |
| `context_follow`          | Answer uses perturbed fact                                           |
| `memory_override`         | Answer uses original fact despite fully perturbed context            |
| `conflict_awareness`      | Answer explicitly notes uncertainty or conflict with prior knowledge |
| `both_claims`             | Answer mentions both original and perturbed facts                    |
| `unrelated_or_failed`     | Answer avoids or misses the relevant claim                           |
| `refusal_or_insufficient` | Model says evidence is insufficient                                  |

Store entailment labels separately:

```json
{
  "core_id": "garage_core_000123",
  "model": "gpt",
  "generation_id": "gen_000456",

  "answer_perturbed_context": "...",

  "entails_original_claim": true,
  "entails_perturbed_claim": false,
  "mentions_conflict": false,

  "cites_modified_passage": true,
  "citation_supports_claim": false,

  "generator_behavior_label": "memory_override",

  "closed_book_knows_original": true,
  "closed_book_confidence_mean": 0.86
}
```

Now Generator track can answer:

```text
When models know the original fact closed-book, do they override fully consistent contradictory retrieved evidence more often?
```

Key Generator track metrics:

| Metric                        | Computation                                                   |
| ----------------------------- | ------------------------------------------------------------- |
| Context adherence rate        | % `context_follow`                                            |
| Memory override rate          | % `memory_override`                                           |
| Conflict awareness rate       | % `conflict_awareness`                                        |
| Citation misuse rate          | cited modified passages but answered with original fact       |
| Memory-conditioned override   | override rate when `closed_book_knows_original = true`        |
| Perturbation-type sensitivity | rates by entity/date/number/relation/etc.                     |
| Popularity sensitivity        | rates by Head/Torso/Tail                                      |
| Global context resistance     | override rate despite no original answer leakage in grounding |

This version creates a stronger Generator track because the provided context is not self-conflicting.

# Step 11: Create Judge-pairing track view — judge pairing

Judge-pairing track should use generated answers from Generator track, but it should not be framed around parametric memory. It should be framed around **factual error detection by judges**.

Create judge tasks from two answer groups.

## Group 1: induced-error answers

These are answers where the generator followed the fully perturbed context.

```text
generator_behavior_label = context_follow
```

Relative to the original GaRAGe source, these answers contain a known induced factual error.

Gold judge label:

```json
"has_induced_error": true
```

## Group 2: correct-control answers

These are answers where the generator used the original fact correctly.

```text
generator_behavior_label = memory_override
```

For Judge-pairing track, do not call them memory overrides in the task data. They are simply source-correct answers relative to the original evidence.

Gold judge label:

```json
"has_induced_error": false
```

This gives judges both positive and negative cases, which lets you measure false positives.

You can also include a third group:

## Group 3: ambiguous/conflict-aware answers

These are answers where the generator says the evidence differs from known facts, or mentions both claims.

```text
generator_behavior_label in ["conflict_awareness", "both_claims"]
```

These can be used as a harder calibration set, but I would keep them out of the main Judge-pairing track metric initially.

# Step 12: Construct judge input

Each judge receives:

```text
Question
Answer to evaluate
Original authoritative grounding passages
Instruction to detect factual errors
```

The judge does **not** receive:

```text
gold answer
perturbed passages
perturbation metadata
generator model name
whether this is same-model or cross-model
```

The judge should be blind to generator identity. You record generator identity externally.

Judge prompt:

```text
You are evaluating whether an answer is factually supported by the provided source passages.

Question:
{question}

Answer:
{generated_answer}

Source passages:
{all_grounding_original}

Task:
1. Decide whether the answer contains any factual claim contradicted by the source passages.
2. Identify the specific unsupported or contradicted claim.
3. Identify the source passage ID that supports your judgment.
4. Return JSON only.

JSON format:
{
  "verdict": "correct" | "incorrect" | "unclear",
  "contains_factual_error": true | false,
  "wrong_claim": "...",
  "supporting_source_passage_id": "...",
  "explanation": "...",
  "confidence": 0.0
}
```

Because every answer-containing passage was perturbed during generation, a judge evaluating against original grounding is testing whether it can catch the induced factual error, not whether it can resolve mixed evidence.

# Step 13: Label judge pair type

For every judge verdict, attach pair metadata externally:

```json
{
  "judge_task_id": "judge_000789",
  "core_id": "garage_core_000123",
  "generation_id": "gen_000456",

  "generator_model": "claude-sonnet",
  "judge_model": "claude-opus",

  "pair_type": "same_family",
  "same_exact_model": false,
  "same_provider_family": true,

  "has_induced_error_gold": true,
  "error_type_gold": "temporal",
  "wrong_claim_gold": "...",
  "source_span_gold": "...",

  "judge_contains_factual_error": true,
  "judge_wrong_claim": "...",
  "judge_localized_error": true,
  "judge_confidence": 0.91
}
```

Pair types:

| Pair type        | Definition                                          |
| ---------------- | --------------------------------------------------- |
| `same_model`     | generator and judge are same exact model            |
| `same_family`    | same provider/model family but not exact same model |
| `cross_family`   | different provider family                           |
| `open_to_closed` | open generator, closed judge                        |
| `closed_to_open` | closed generator, open judge                        |

For Judge-pairing track, main metrics:

| Metric                    | Definition                             |
| ------------------------- | -------------------------------------- |
| Error detection precision | Judge flagged error and error was real |
| Error detection recall    | Judge caught real induced errors       |
| F1                        | Standard detection F1                  |
| False positive rate       | Judge flagged correct-control answer   |
| Localization accuracy     | Judge identified mutated claim/span    |
| Same-model delta          | same-model F1 minus cross-family F1    |
| Same-family delta         | same-family F1 minus cross-family F1   |
| Calibration               | confidence vs correctness              |

Use these four perturbation types first:

```text
entity substitution
temporal shift
numerical shift
relation/affiliation change
```

That gives:

```text
200 examples
× 3 generator models
= 600 perturbed RAG answers

600 answers
× 3 judge models
= 1,800 judge decisions
```

The main added cost is perturbation validation, because each example may require editing multiple passages. But the payoff is large: your perturbed context becomes internally consistent, which makes the parametric-memory claim cleaner.

# Most important rule

For every example, preserve this causal chain:

```text
original answer-containing passages
→ answer-causal atomic claim
→ all source mentions of the claim
→ globally consistent perturbation
→ fully perturbed grounding set
→ generator answer
→ generator behavior label
→ judge task
→ judge detection label
```

Generator track uses:

```text
fully perturbed grounding → generator behavior
```

Judge-pairing track uses:

```text
generator answer → judge detection behavior against original grounding
```

Same core data, two different scientific objects.
